In action

Overview

When looking for recommendations for places we travel, we save a bunch of videos — and it quickly becomes overwhelming to open each one and decide if it's worth keeping. This feature collects, validates, and summarises TikTok travel content so it can be consumed efficiently inside a wider trip planner.

In one sentence: the service analyses the video, extracts data, validates it, removes hallucinations, stores the result, and returns processed insights visualised on a map. Phase 1 shipped with link paste only; TikTok share and carousel formats were scoped as later entry points.

The problem

Saved travel TikToks are unstructured. Captions, spoken tips, location tags, and comments all carry signal — but none of it is ready for a planner. Users need a reviewable summary and typed entities (cafés, neighbourhoods, logistics) they can trust on a map, not a wall of links.

The hard part isn't calling an LLM. It's separating travel from noise, never trusting the model for coordinates, and making slow processing feel reliable when ingestion and Gemini can take far longer than a normal API request.

Scope & constraints

Initial restrictions

  • ✱No cost — rate limiting and a cap of ~10 analyses per user (not built for scale or commercial use yet)
  • ✱Core feature first — functional pipeline starting with pasted links only
  • ✱v1.5 nice-to-have — TikTok share sheet entry + photo carousel support
  • ✱Smart itineraries — group locations into coherent day plans (future)

Two entry points (planned)

  1. TikTok share — user finds a video, saves it, and the service ingests it from the share flow
  2. Paste link — user pastes a URL; the service processes it directly (phase 1)

My approach

I designed the pipeline as stages with clear contracts: ingest → semantic extraction → geocode validation → assembly. Each stage has one job. Coordinates never come from the LLM — only from a dedicated geocoding pass.

Caching & async jobs

LLM processing makes requests slow. The API enqueues background jobs and returns `202` for new URLs; clients poll `GET /v1/analyses/{id}` until `completed` or `failed`. Duplicate URLs hit a URL cache and return `200` immediately with `meta.from_cache: true`.

ScenarioHTTPClient action
Same URL already processed200Use result — no poll
New URL202Poll until completed or failed

Orchestrator abstraction

The job orchestrator is an abstract interface so the implementation can change when constraints change — e.g. swap in-memory queuing for Redis without rewriting the pipeline. For phase 1 constraints, a simple orchestrator was enough; the boundary was the investment.

API design

GET/v1/analyses?trip_id={id}List completed videos for a trip
DELETE/v1/analyses/{id}Remove analysis + insights
GET/v1/healthLiveness

POST body carries `source_url`, optional `trip_id`, and options like `drop_unverified_geo`. Validation and routing happen before any LLM call — bad URLs fail fast; cache hits never re-run the pipeline.

LLM extraction

Gemini turns unstructured TikTok content into a typed ExtractionResult: a video-level summary (headline, description, vibe tags) plus an array of TravelInsight items — places, areas, tips, logistics, cultural notes, warnings, activities — with no coordinates from the model.

What goes into the model

FieldRole
TranscriptPrimary signal — full spoken text
transcript_sourceProvenance (tiktok_auto_caption, whisper, manual)
source_urlContext only — not analysed as caption text
media_typeUsually video

Thumbnail, creator, and title from ingest are not sent to Gemini. The prompt instructs the model to analyse only the transcript — ignore captions and hashtags unless they appear verbatim in the spoken text.

Structured output

Gemini is configured with a fixed system prompt, `response_mime_type: application/json`, and a Pydantic JSON schema (`ExtractionResult`). Temperature is kept low (0.2) for deterministic extraction. Field descriptions on the schema act as secondary instructions to the model.

  • ✱Model fallback chain (primary → fallback → built-in defaults)
  • ✱Retries on transient errors (429, 503, quota)
  • ✱API budget check before each call (`gemini_max_requests_per_analysis`)

Anti-hallucination rules

  • ✱Output only JSON matching the schema — no free-form prose
  • ✱One insight per distinct venue; prefer specific names over vague references
  • ✱Include address only when mentioned or highly confident — never output lat/lng
  • ✱human-readable sentences for highlights and action_items; kebab-case only for semantic_tags
  • ✱is_travel_related gate — non-travel content (dance trends, skincare, etc.) returns empty insights and the pipeline fails with `CONTENT_NOT_TRAVEL`

Example extraction shape

For a Sydney café crawl video, the model might return a headline like "3 hidden cafés in Sydney", vibe tags `food`, `hidden-gem`, and insights mixing place entities (AP Café with scope venue/city/country) and logistics entities (Opal card tips) — all without coordinates until geocoding runs.

Geocoding validation

After semantic extraction, a separate geocoding pass adds verified coordinates. The LLM might say "AP Bakery, Sydney, Australia"; Nominatim either returns lat/lng or it doesn't.

For each geo insight, the service builds a forward-geocode query — e.g. `{title}, {scope.city}, {scope.country}` — with normalized cache keys (lowercase, stripped punctuation) separate from the human-readable query sent to the provider.

  • ✱verified: true — coordinates attached with geocoder metadata (provider, display_name, confidence)
  • ✱verified: false — coordinates null; with `drop_unverified_geo: true` (default), places stay out of `insights[]` for map clients and appear in `meta.unverified_geo` for transparency

The orchestrator merges LLM output and geocode results into a final AnalysisResponse: source metadata, summary, verified insights, and `meta` with processing stages, insight counts, geo counts, and cache flags.

Challenges

  • ✱TikTok ingest — downloading media often needs cookies or nightly yt-dlp; I shipped audio → Whisper as the primary path with manual transcript paste as fallback
  • ✱Pronunciation & place names — creators mispronounce locations; transcript text alone often can't resolve a valid geocode even when the recommendation is real
  • ✱Latency vs UX — async jobs and polling were non-negotiable once LLM + ingest landed in the same request path

Working with agents

I co-planned the initial system design with Cursor and Claude — exploring the problem statement, core behaviour, and constraints. Agent skills helped surface edge cases I hadn't written down yet (cache semantics, content gates, job states).

Agents were strong at boilerplate: repetitive schema work, API stubs, test scaffolding. They were weaker when I needed cohesive system thinking — class diagrams that mixed unrelated discussions, or documentation that ballooned minor points into paragraphs that sounded intelligent but didn't help implementation.

  • ✱Use agents for schema definitions, route stubs, and repetitive component patterns
  • ✱Keep architecture decisions and pipeline contracts in my own words — review every diagram
  • ✱Treat generated docs as drafts; cut aggressively before they become the source of truth
